# Архитектура: решения и ограничения

## Поиск по названию: возможности и потолок

Основной поиск — по артикулу: он полный и надёжный, артикул однозначно адресует деталь
в API. Поиск по названию — вспомогательный: он работает по встроенному справочнику
имя→артикул и не гарантирует полноту.

Почему так. API «Проценка» ищет только по точному артикулу: ни поиска по названию, ни
перечисления номенклатуры у него нет. Значит, полный справочник имя→артикул через это
API получить нельзя — чтобы запросить артикул, его надо уже знать. Справочник наполняем
доступным способом: стартовый seed (собран один раз от нескольких ходовых легковых
артикулов) плюс самообучение — каждый обычный поиск по артикулу дописывает увиденные
пары в локальный индекс браузера. Поэтому справочник — это выборка, а не вся база:
название может не найтись просто потому, что его в выборке ещё нет.

Вдобавок у сервиса есть квоты (как минимум на грузовой ассортимент), поэтому массовый
сбор справочника через API невозможен — ещё одна причина держать seed маленьким и
опираться на самообучение.

Вторая причина неполноты — у API нет применимости к автомобилю. Одно название
соответствует сотням разных деталей (например, «Фильтр масляный» — 270 позиций в одной
выдаче), и сервис не говорит, какая подходит к конкретной машине. Поэтому поиск по
названию показывает кандидатов по категории, но не подбирает деталь под авто. Названия
в данных к тому же неоднородны (дубли, «уценка», лишние пробелы) — совпадение приблизительное.

Что подняло бы потолок:
- Выгрузка номенклатуры/прайса от поставщика (файл) — загрузили бы полную базу
  имя→артикул. Чистое решение, упирается в данные, которых у нас нет.
- Либо отдельный эндпоинт поиска по названию на стороне поставщика.
- Либо отраслевой кросс-каталог класса TecDoc с применимостью к авто — настоящий подбор
  «деталь на мою машину». Лицензируется, за рамками теста.

Сервер с базой данных сам по себе потолок не поднимает: он хранит данные, а не создаёт
их, и оправдан только при появлении одного из источников выше. До тех пор справочник
держим на клиенте — это легче и честнее по объёму.

## Как определяется режим поиска

Одно поле ввода, режим выбирается по содержимому:

- есть цифры — это артикул, запрос уходит в API. Сюда же попадает артикул, набранный
  русскими буквами, похожими на латинские («ОС90»): API его понимает;
- цифр нет — ищем по справочнику названий, без запросов к API;
- в справочнике пусто — всё равно пробуем как артикул.

Не поддерживается: название вместе с цифрами («колодки 2109») уходит в поиск по артикулу
и, как правило, ничего не находит.

Стартовый справочник (`src/catalog/seed.json`) собирается скриптом `scripts/build-seed.mjs`
через dev-прокси: только легковые артикулы, один запрос аналогов на артикул, не больше
10 запросов. Он грузится отдельным чанком при первом поиске по названию.
