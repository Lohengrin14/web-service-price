# Архитектура: решения и ограничения

## Поиск по названию: возможности и потолок

Основной поиск — по артикулу: он полный и надёжный, артикул однозначно адресует деталь
в API. Поиск по названию — вспомогательный: он работает по встроенному справочнику
имя→артикул и не гарантирует полноту.

Почему так. API «Проценка» ищет только по точному артикулу: ни поиска по названию, ни
перечисления номенклатуры у него нет. Значит, полный справочник имя→артикул через это
API получить нельзя — чтобы запросить артикул, его надо уже знать. Справочник наполняем
доступным способом: стартовый seed (собран один раз от нескольких ходовых легковых
артикулов) плюс самообучение — каждый обычный поиск по артикулу дописывает увиденные
пары в локальный индекс браузера. Поэтому справочник — это выборка, а не вся база:
название может не найтись просто потому, что его в выборке ещё нет.

Вдобавок у сервиса есть квоты (как минимум на грузовой ассортимент), поэтому массовый
сбор справочника через API невозможен — ещё одна причина держать seed маленьким и
опираться на самообучение.

Вторая причина неполноты — у API нет применимости к автомобилю. Одно название
соответствует сотням разных деталей (например, «Фильтр масляный» — 270 позиций в одной
выдаче), и сервис не говорит, какая подходит к конкретной машине. Поэтому поиск по
названию показывает кандидатов по категории, но не подбирает деталь под авто. Названия
в данных к тому же неоднородны (дубли, «уценка», лишние пробелы) — совпадение приблизительное.

Что подняло бы потолок:
- Выгрузка номенклатуры/прайса от поставщика (файл) — загрузили бы полную базу
  имя→артикул. Чистое решение, упирается в данные, которых у нас нет.
- Либо отдельный эндпоинт поиска по названию на стороне поставщика.
- Либо отраслевой кросс-каталог класса TecDoc с применимостью к авто — настоящий подбор
  «деталь на мою машину». Лицензируется, за рамками теста.

Сервер с базой данных сам по себе потолок не поднимает: он хранит данные, а не создаёт
их, и оправдан только при появлении одного из источников выше. До тех пор справочник
держим на клиенте — это легче и честнее по объёму.

## Как определяется режим поиска

Одно поле ввода, режим выбирается по содержимому:

- есть цифры — это артикул, запрос уходит в API. Сюда же попадает артикул, набранный
  русскими буквами, похожими на латинские («ОС90»): API его понимает;
- цифр нет — ищем по справочнику, без запросов к API: слова запроса ищутся и в названии
  детали, и в производителе («bosch», «колодки brembo»). Производители в данных записаны
  латиницей, поэтому их ищут латиницей; русские написания («бош») не распознаются;
- в справочнике пусто — всё равно пробуем как артикул.

Не поддерживается: название вместе с цифрами («колодки 2109») уходит в поиск по артикулу
и, как правило, ничего не находит.

Стартовый справочник (`src/catalog/seed.json`) собирается скриптом `scripts/build-seed.mjs`
через dev-прокси: только легковые артикулы, один запрос аналогов на артикул, не больше
10 запросов. Он грузится отдельным чанком при первом поиске по названию.

## Ключ API и деплой
Сейчас демо на GitHub Pages обращается к API напрямую, без прокси, с публичным
демо-ключом из документации (00000000-0000-0000-0000-000000000001). Этот ключ не
секрет — он приведён в официальной документации, — поэтому его наличие в клиентском
бандле допустимо как осознанное исключение. API отдаёт HTTPS и CORS `*`, так что
браузер ходит в него напрямую и отдельный сервер для демо не нужен.

Когда поставщик выдаст настоящий ключ покупателя, он НЕ должен попадать в бандл. Тогда:
- поднимается серверный прокси (локально его роль играет dev-прокси Vite; в проде —
  serverless-функция в РФ-доступном облаке, напр. Yandex Cloud Function), который
  хранит ключ в переменных окружения и подставляет в запрос;
- во фронте VITE_USE_DEMO_KEY=false, а VITE_API_URL указывает на прокси;
- прокси пропускает к API только number, brand, analogues, info.

## Почему прокси

Обычный путь запроса — через прокси: браузер ходит на свой адрес `/api/search`, а прокси
пересылает запрос в API и сам подставляет ключ. Локально прокси — это dev-сервер Vite
(`vite.config.js`). Прокси решает три задачи:

- **прячет ключ**: он живёт в переменных окружения сервера и не попадает ни в бандл, ни в git;
- **обходит CORS**: для браузера запрос идёт на тот же сайт, ограничения чужого домена его не касаются;
- **убирает mixed content**: страница по HTTPS не может ходить на HTTP-адрес, а прокси может.

Плюс белый список параметров: к API уходят только `number`, `brand`, `analogues`, `info`,
поэтому через прокси нельзя подменить ключ или передать что-то лишнее.

Для демо две последние задачи отпали сами: API работает по HTTPS и отдаёт CORS `*`. Осталась
только первая, а демо-ключ не секрет — поэтому статика на GitHub Pages ходит в API напрямую
(см. «Ключ API и деплой»). С настоящим ключом прокси снова обязателен.

## API ищет только по артикулу — что из этого следует

У «Проценки» один способ найти деталь — точный номер. Отсюда устройство интерфейса:

- **два этапа**: по номеру — список производителей (один номер у разных брендов — разные детали),
  по номеру и бренду — сама деталь, её склады и аналоги. Второй запрос делаем с номером и брендом
  из ответа первого, а не с тем, что набрал пользователь;
- **первый производитель выбирается сам** (с наибольшим остатком) — чтобы результат был виден сразу;
- **нормализация ввода**: API и сам понимает `oc90`, `OC 90`, `OC-90`, но мы приводим ввод к одному
  виду, чтобы не запрашивать одно и то же дважды и держать ссылку чистой;
- **поиск по названию и производителю** возможен только по своему справочнику — см. раздел выше.

## Гонки запросов, дедуп и кеш

- **Устаревшие ответы игнорируются.** У каждого запроса свой `requestId` (thunk'и Redux Toolkit);
  в стор записывается только ответ на последний запрос. Если пользователь успел начать новый поиск,
  старый ответ, пришедший позже, ничего не перетрёт. Авто-выбор производителя тоже проверяет,
  что ответ ещё актуален.
- **Дедуп.** `condition` у thunk'ов не отправляет запрос, если тот же поиск уже найден или идёт
  (повтор после ошибки — можно). Артикулы сравниваются по каноническому ключу (`canonicalNumber`:
  только буквы и цифры в верхнем регистре), так что `OC 90` и `OC-90` — один запрос.
- **Кеш ответов на время сессии**: 5 минут, до 20 ответов, только успешные. «Назад», «вперёд» и
  возврат к уже открытому производителю не тратят запросы — это важно, потому что ключ общий
  и у API есть квота.
- **Пауза перед автопоиском** — секунда после ввода: меньше промежуточных запросов, пока человек печатает.
- **Фильтры и сортировка** — мемоизированный селектор по всей выдаче; на страницу (подгрузка при
  прокрутке) обрезаем в последнюю очередь, поэтому «Лучшая цена» и сортировка честные.

## Что отклонили

- **Скрейпинг розничного сайта favorit-parts.ru.** Это не документированная «Проценка», а внутреннее
  устройство чужого сайта: оно может поменяться без предупреждения, и браузер с нашего домена туда
  не пустит (CORS) — понадобился бы свой сервер. И главное — копирование витрины выдавало бы наш
  проект за Фаворит. Используем только документированное API и честно указываем источник данных.
- **Сервер с базой данных для справочника названий** — сам по себе потолок не поднимает (см. выше).
- **Библиотеки** (i18next, роутер, UI-киты, нечёткий поиск): задачи решаются парой функций,
  а ТЗ просит «чем проще, тем лучше».
